# Principles

- Correctness over speed.
- Produce the smallest complete, production-ready solution.
- Prefer simple, explicit, idiomatic code.
- Optimize for maintainability, clarity, and performance.
- Solve the complete problem, not just the immediate symptom.

# Coding session initialization

At the start of a newly created coding session, treat initialization as a
blocking pre-response gate. Complete it before the first commentary message,
planning, repository inspection, shell or network commands, or any other task
action. Only the minimum capability lookup needed to locate the host's
thread-title and thread-pin operations may precede it.

1. Invoke the available thread-title operation using:

   `[<project>] <description>`

2. After the title action resolves, invoke the available thread-pin operation.
3. Verify each result from returned host state when that state is available.

Rules:

- Use the current repository name as `<project>`, derived from repository or
  working-directory context supplied by the host. Do not inspect the repository
  merely to choose the title.
- Keep `<description>` lowercase and at most four words.
- Both operations are required and ordered. Do not defer either supported
  operation to a later interaction.
- Distinguish success from an unsupported or unavailable capability and an
  operation failure.
- Resolve both actions in order even when the first cannot succeed. Do not
  silently skip an operation or retry indefinitely.
- When either result is not successful, begin the first commentary with
  `Thread initialization: rename <status>; pin <status>.` and include a concise
  reason for each non-success status.
- After that fail-visible status, continue the user's substantive request.
  Unsupported or failed session management must not deadlock unrelated work.

# Repository context and mutation gate

Start repository work at `docs/agents/README.md` when present. Follow its
routing and load only guidance relevant to the current decision.

Before every repository mutation in a newly created or resumed session:

1. Load `docs/agents/GUARDRAILS.md` and
   `docs/references/rules/work-lane-gating.md` when each is present and relevant
   to the pending decision. A repository mutation makes both relevant.

2. Complete read-only safety recon:
   - inspect the current directory, branch, dirty state, remote, default/base
     branch, active pull requests, registered worktrees, and exact primary
     checkout;
   - inspect repo-local delivery rules and current human Git/GitHub identity;
   - preserve every unrelated or ambiguous change.

3. Ask exactly:

   > Before I make any repository changes, should I create a new GitHub issue, `GH-<issue-number>` branch, canonical worktree, and pull request for this work, or continue in the existing branch/worktree and land it through that branch's pull request?

   Interpret the response's first standalone token after trimming surrounding
   whitespace, case-insensitively: `c` means continue existing, while `n` or
   `y` means new lane. When shorthand leads a longer response, shorthand is the
   primary lane choice and the remaining text is supplemental lane
   instructions. Continue accepting explicit full-form choices; ambiguous or
   contradictory responses fail closed.

4. Wait for the user's explicit choice unless that exact choice is already
   recorded for the same unit of work.

5. Record or verify a complete Pull-Request Landing Plan before every
   repository mutation with:
   - repository;
   - issue to create or reuse;
   - exact branch;
   - non-primary owning worktree;
   - protected base branch;
   - ready pull request to create or existing pull request to update;
   - scope match and any unknowns or blockers.

6. Establish or verify that lane before any repository file or delivery
   mutation.

Rules:

- The gate covers source, tests, documentation, specs, plans, configuration,
  generated artifacts, and every other repository file.
- It also covers issue, branch, worktree, staging, commit, push, pull-request,
  and merge mutations.
- Read-only discovery, review, capability inspection, context resolution, and
  native planning may precede the choice. Write-capable commands may not.
- Do not infer the choice from a clean default branch, issue reference, dirty
  feature branch, or generic request to create a pull request.
- One recorded choice covers directly required tests, documentation,
  validation fixes, review fixes, and delivery. Ask again before materially new
  or tangential work.
- If the user chooses a new lane, create or reuse one human-assigned GitHub
  issue, exact `GH-<issue-number>` branch, canonical linked worktree, and one
  ready-pull-request plan before editing files.
- If the user chooses to continue, prove the non-protected branch, its exact
  owning linked worktree, issue scope, protected base, and create-or-update
  pull-request target. Reuse the existing pull request when one exists.
- The GitHub issue tracks the unit of work and provides a stable identifier for
  the branch, commits, and pull request. It is not the source of implementation
  requirements.

## Merge authorization

- A Pull-Request Landing Plan proves a delivery lane; it does not authorize
  merge.
- Merge authority requires a direct user request or an accepted bounded merge
  plan naming the exact pull-request set.
- Before any merge or merge-queue mutation, resolve `pull-request-merge` and
  load `docs/references/rules/github-pr-merge.md`.
- Before every merge wave, reconcile the authorization source, authenticated
  actor, expected head and base, repository policy, current reviews and checks,
  dependencies, and infrastructure or deployment effects.
- Only exact current `MERGE_READY` nodes may merge. Pending, missing,
  stale-head, or policy-ineligible skipped checks are not passing. Never bypass
  protection, reviews, required checks, a merge queue, repository policy, or
  identity safeguards.

# Execution environment

- Canonical writable worktrees live at
  `~/worktrees/<owner>/<repository>/<lane>`; never put a worktree inside a
  repository.
- Use exact `GH-<issue-number>` for durable issue work.
- Use uppercase detached `PR-<number>` only for temporary pull-request
  inspection. Reuse the pull request's same-repository head branch for writable
  repair.
- Before creating a worktree, inspect registered worktrees and reuse the exact
  branch worktree when one exists.
- Use native `git worktree` commands and ordinary filesystem operations as the
  portable authority; optional wrappers are manual conveniences only.
- Treat the clone's primary/root checkout as read-only for coding-agent work,
  regardless of its branch, cleanliness, or planned pull request. Never edit, generate, stage, commit, or switch branches there with a plan to move the diff later.
- Work only in the user-selected non-primary writable lane.
- Never stash, reset, clean, force-remove, or delete a branch to create or
  clear a worktree.
- Link the primary checkout's `.env` and `.envrc` into writable lanes by
  default when each exists, using only exact verified symlinks; omit both links
  when isolation is required.
- Never copy environment contents or overwrite destination environment
  material. Preserve a repository- or user-supplied `.envrc`; direnv approval
  remains path-specific.
- Treat working files, the index, and `HEAD` as worktree-local; treat objects,
  refs, remotes, configuration, and stash entries as shared clone state.
- Before edits, inspect the selected worktree and preserve changes not created
  for the current request.
- If an ungated or primary-checkout change is detected, stop and preserve it.
  Do not stage, commit, push, stash, reset, clean, discard, or silently transfer
  it. Ask the lane question and prove exact recovery ownership before any
  further mutation.

# Deletion safety

Before designing deletion behavior or deleting persistent project, user,
business, or external-system state, load
`docs/references/rules/deletion-safety.md` when present.

Rules:

- An unqualified delete means soft delete. Use a reversible lifecycle state
  with a supported, authorized, and tested restore path.
- Task-owned ephemeral scratch that never became authoritative state is outside
  this retained-state definition. Treat ambiguous state as covered.
- Treat purge, destroy, force deletion, empty-trash operations, destructive
  replacement, history rewrite, retention expiry, backup or snapshot deletion,
  cryptographic erasure, and irreversible cascades as hard delete.
- Make the normal product and operational path soft-delete by default. Keep
  hard delete as a separate privileged, auditable, server-enforced action.
- Before any hard delete, resolve and present exact targets, or a bounded
  selector first resolved to the exact current target set with its current
  count and materialized target IDs or an immutable snapshot/version token,
  environment, cascades, why soft delete is insufficient, loss of restore,
  backup state, retention or legal impact, and the verification plan.
- After that outline, obtain a specific manual confirmation from the human for
  those exact current targets.
- Initial requests, general task or plan approval, automation, retention
  schedules, prior soft-delete approval, and broad cleanup language do not
  count as hard-delete confirmation.
- Bind confirmation to actor, action, exact targets or immutable
  snapshot/version, environment, and consequences. Immediately before
  execution, compare the current target set or version with the confirmed
  snapshot; any difference requires a new outline and confirmation.
- Preserve stricter repository, legal, privacy, security, infrastructure, and
  provider controls. One post-outline confirmation may satisfy multiple
  deletion gates only when the combined outline is complete.

# Execution

- Read project instructions and local conventions before editing.
- Investigate the relevant codebase before making changes.
- When `kit context resolve` behavior is not already established, run
  `kit capabilities context resolve --json` before choosing or running the
  command.
- Before implementation, maintenance, pull-request repair, or repository
  bootstrap, run `kit context resolve --workflow <slug> --json` with relevant
  `--feature` and `--path` hints. Load every selected artifact that is required
  before acting, and rerun resolution after material scope changes.
- Use native planning for research, clarification, design, and the accepted
  plan. Before implementation, inspect relevant code and repository memory,
  then decide whether material rationale requires creating or adopting
  `docs/specs/<feature>/SPEC.md`. When required, capture the accepted native
  plan there before editing implementation files; when code and tests preserve
  the complete durable truth, do not create documentation only for process.
- Before implementation or validation, including browser automation and
  browser testing, load `docs/references/rules/testing-and-environment-validation.md`
  and the project's `docs/references/testing.md`.
- Before editing implementation/source or test files, load
  `docs/references/rules/source-file-size.md`. Keep eligible
  handwritten source and test files at 300 physical lines or fewer. Audit the
  complete affected scope before delivery.
- Prefer repository evidence over assumptions. Infer intent from existing
  code, tests, documentation, and conventions whenever possible.
- Own the requested outcome. Complete all code, tests, configuration,
  documentation, refactoring, and supporting changes necessary for it to work.
- Resolve routine implementation decisions independently using repository
  evidence, project conventions, and the simplest reasonable approach.
- Continue until the outcome is complete or blocked by missing information,
  permissions, or external dependencies.
- If an approach fails, diagnose the cause, revise it, and continue.
- If blocked, complete unblocked work first, then report the blocker,
  supporting evidence, why it cannot be resolved locally, and the smallest
  action required.
- Ask questions only when the answer materially changes implementation and
  cannot be determined from repository evidence or reasonable inference.

# Debugging

- Identify the root cause before implementing a fix.
- Prefer fixes that eliminate the underlying issue rather than masking it.
- Remove obsolete or unnecessary code when appropriate.

# Design

- Default to the simplest solution that completely satisfies the requirements.
- Preserve existing architecture, behavior, interfaces, and conventions unless
  change is necessary for the current request.
- Briefly explain tradeoffs only when they materially affect implementation or
  future maintenance.

# Validation

- Review all changes before finishing.
- Run all relevant tests, builds, type checks, linting, formatting, and other
  project validation appropriate for the affected code.
- Validate the requested outcome end to end whenever practical.
- Do not treat a successful build or narrow test as sufficient evidence that
  the request is complete.
- Resolve issues introduced by the changes before completion.
- State exactly what could not be validated and why.

# Repository memory completion

- After implementation and validation, load
  `docs/references/rules/constitution-curation.md` when present and curate
  durable rationale into the appropriate repository documents.
- Every implementation final response must include `Repository Memory`,
  `Decision`, `Rationale`, and `Artifacts` in addition to outcome, validation,
  and remaining risks.

# Pull request

- After implementation and validation, create the one planned ready pull
  request when none exists or update the existing pull request selected by the
  user.

# Communication

- Keep progress updates brief and limited to significant findings, completed
  milestones, blockers, or changes in approach.
- Lead final responses with:
  1. Outcome
  2. Validation performed
  3. Remaining risks, assumptions, or recommended follow-up work

# Agent completion output

This section defines the terminal response order and supersedes the earlier
three-item final-response ordering without removing any required evidence.

Before a terminal task completion or handoff response, load
`docs/references/rules/agent-completion-output.md` when present. Do not apply
this format to progress commentary or a focused clarification question.

Rules:

- Make the first human-readable line
  `# PASS|PARTIAL|BLOCKED|FAIL — <one-sentence outcome>`. A required host
  wrapper may surround it, but no human-readable preamble may precede it.
- Immediately follow with a table whose columns are
  `Type | Action required | Why | Continue with`.
- Order rows Blocker, Incomplete, Next, Optional, then None. Every PASS includes
  a None row stating that no action is required.
- Make required follow-ups copy-ready. Never leave cells blank or hide blockers
  and incomplete work below completed detail.
- Use PASS only for complete scope and required validation, PARTIAL for usable
  incomplete work, BLOCKED for a specific external dependency, and FAIL for an
  unresolved known failure without an external stopping dependency.
- Preserve native evidence states such as PENDING, UNKNOWN, SKIPPED, and
  NOT_APPLICABLE literally.
- Select one primary profile from the requested deliverable: implementation,
  research, diagnosis, planning, validation, review, operations, coordination,
  or fallback.
- Keep tables compact and preserve every field required by active delivery,
  validation, repository-memory, orchestration, program, and environment
  contracts inside the canonical profile tables.
